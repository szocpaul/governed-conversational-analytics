# Feature Specification: Synthetic Ticket Texts

**Feature Branch**: `[009-synthetic-ticket-texts]`

**Created**: 2026-10-12

**Status**: Draft (revised 2026-10-12 for LLM-based generation per human decision; supersedes the hand-authored-template draft of the same day)

**Input**: User description: "Generate three synthetic free-text fields per ITSM ticket — short_description, description, resolution_notes — using the project's local pinned Qwen model, so the currently purely structured dataset gains realistic text for a later hybrid-search feature. Generation is an explicit, versioned, auditable offline pipeline: the pinned model (exact model ID, temperature 0, recorded seed, no fallback) produces strictly validated structured JSON via a typed DSPy program, batched with checkpoint/resume and fail-loud behavior; a deterministic, model-free validation suite is the quality gate; the output artifact is pinned, checksummed, and immutable once human-approved; the tickets table gains the three generated columns via an atomic import approved only after human data-quality review; and the three columns are exposed read-only through the governed query layer. See specs/009-synthetic-ticket-texts-sketch.md and the human revision decision of 2026-10-12."

## Background

The pinned ITSM dataset is purely structured (19 columns, no free text), so meaningful hybrid search is impossible today. This feature adds the text foundation: synthetic, English-only ticket texts generated by the project's local pinned language model under the same pinning, provenance, and artifact discipline as the rest of the project. The hybrid search itself is a follow-up feature and out of scope here.

Verified ground truths from the pinned dataset (`data/raw/tickets.csv`):

- 2057 tickets across 5 categories and exactly 20 category x sub_category pairs; priorities P1-P4.
- 250 tickets are open (`closed_at` empty); 1807 are closed.

Human-approved decisions (binding):

1. The `itsm.tickets` table gets the 3 generated columns (marked as generated in schema comments).
2. `resolution_notes` is SQL NULL when the ticket is open (`closed_at IS NULL`).
3. Generated text is English only.
4. **(Revised 2026-10-12)** Generation uses the local pinned llama.cpp Qwen model (exact pinned API model ID, temperature 0, recorded seed, no fallback) through a typed DSPy program with strict JSON schema validation, batched (~5 tickets per call) with checkpoint/resume. The output artifact becomes PINNED, versioned, SHA-256-checksummed, and immutable once human-approved — the same discipline as `artifacts/baseline.json` and `app/ai/optimized_program.json`. Regeneration means a new artifact version, a full run, new checksums, and an updated manifest; never partial, never silent.
5. The 3 new columns are exposed read-only via the governed query layer in THIS feature.
6. **(Added 2026-10-12)** Human data-quality review of generated samples (per category) is REQUIRED before the import is approved — this will be the feature's MANUAL GATE.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Governed LLM text generation with strict validation (Priority: P1)

A data maintainer runs an explicit offline generation step: the local pinned Qwen model reads each ticket's structured columns (category, sub_category, priority, SLA flags, resolution time, reopened, and similar) as prompt context and generates the three text fields per ticket through a typed DSPy program that returns strict JSON (ticket_id plus the three fields), batched at about 5 tickets per model call. Every entry is validated with zero tolerance before acceptance; the run checkpoints after each batch and resumes from the checkpoint after an interruption; invalid entries get bounded retries and then fail loudly. When the run completes, a deterministic, model-free validation suite checks every one of the 2057 entries, and a provenance manifest records exactly which model, versions, seed, and configuration produced the artifact.

**Why this priority**: This is the core of the feature. Without a governed, auditable generation pipeline the synthetic text could not be trusted, and nothing downstream (import, exposure, later hybrid search) could build on it.

**Independent Test**: Run the generation step (including one interrupted-and-resumed run) against the verified local endpoint and verify the completed artifact passes 100% of the deterministic validation suite with a complete provenance manifest. Delivers value even if Stories 2 and 3 are absent (a trustworthy, pinned generated artifact exists).

**Acceptance Scenarios**:

1. **Given** the pinned ticket records and a verified local endpoint (exact pinned model ID, temperature 0, recorded seed), **When** the generation step runs, **Then** it produces exactly one validated entry per ticket (2057 total), in batches of about 5 tickets per model call, and every entry validates against the strict JSON schema before it is accepted.
2. **Given** a run interrupted after some batches, **When** the generation step is restarted, **Then** it resumes from the last checkpoint — it never restarts from scratch and never silently skips tickets.
3. **Given** a model response that fails validation, **When** bounded retries are exhausted, **Then** the run fails loudly with an explicit error; it never fabricates an entry and never skips a ticket.
4. **Given** the completed artifact, **When** the deterministic post-generation validation suite runs (offline, no model calls), **Then** 100% of checks pass: JSON schema conformance; 100% ticket coverage (2057 of 2057, every ticket exactly once); zero empty or unresolved fields; length limits (short_description about 80 characters maximum and one sentence, description 2-4 sentences, resolution_notes 1-3 sentences); English-only; no credential-like or personal-data patterns; consistency with the ticket's structured columns (the text must not contradict them, e.g. no "login issue" text on a Payments ticket); and resolution_notes present exactly for closed tickets.
5. **Given** the completed artifact, **When** the provenance manifest is inspected, **Then** it records the exact API model ID, llama.cpp version, temperature 0, seed, prompt version, DSPy version, generator script hash, batch configuration, row count, output SHA-256, and creation timestamp.
6. **Given** an approved artifact, **When** regeneration is decided (e.g., prompt or model change), **Then** it is a full run producing a NEW artifact version with new checksums and an updated manifest; the previously approved artifact remains intact, and partial or silent regeneration never occurs.

### User Story 2 - Database import of generated fields with provenance (Priority: P2)

A data maintainer rebuilds the local database after the generated artifact has passed the deterministic validation suite AND a human reviewer has approved per-category samples (the feature's MANUAL GATE): the tickets table gains the three generated text columns (clearly marked as generated), the pinned generated artifact is imported atomically together with the pinned ticket data, and the import records the text artifact's provenance. Open tickets carry a genuine SQL NULL in resolution_notes; the pinned source columns remain byte-identical to the pinned raw data.

**Why this priority**: The generated text only becomes queryable once it is in the database under the same atomic-import and provenance discipline as the pinned dataset, and only after human data-quality approval. It depends on Story 1's approved artifact but is independently testable against the database.

**Independent Test**: Reset the database, run the import of the approved pinned artifact, and verify the tickets table has the three new columns populated for all 2057 rows, resolution_notes is NULL exactly for the 250 open tickets, pinned column values match the pinned raw data exactly, and the import manifest references the text artifact's checksum and provenance.

**Acceptance Scenarios**:

1. **Given** a clean database reset and an approved pinned generated artifact, **When** the import runs, **Then** the tickets table contains all 2057 tickets with the three generated columns populated (resolution_notes NULL exactly where the ticket is open), and the import either completes fully or leaves no partial state (atomic).
2. **Given** the imported data, **When** pinned columns are compared against the pinned raw ticket records, **Then** they match exactly — generation is additive only and never modifies pinned data.
3. **Given** a completed import, **When** the import runs again, **Then** the result is identical (idempotent) and the clean local reset path still works unchanged.
4. **Given** a completed import, **When** the import manifest is inspected, **Then** it references the generated text artifact's checksum and provenance manifest in addition to the existing pinned-data provenance.
5. **Given** a generated artifact that has NOT passed the human data-quality review, **When** import approval is considered, **Then** the import is not approved — human review of per-category samples is a required gate, not a formality that can be skipped.

---

### User Story 3 - Read-only governed exposure of the new columns (Priority: P3)

An analyst can retrieve the three generated text fields through the governed query layer — for example listing short descriptions of recent P1 tickets, or finding open tickets where resolution notes are missing — while every write attempt through the governed layer remains rejected.

**Why this priority**: Read-only exposure completes the data foundation so the follow-up hybrid-search feature can build on it without revisiting governance. It is the smallest slice and depends on Stories 1 and 2.

**Independent Test**: Through the governed query layer, select the three new columns with filters (including an is-null filter on resolution_notes) and confirm results are returned; confirm all write operations are still rejected with zero database changes.

**Acceptance Scenarios**:

1. **Given** the imported database, **When** a governed read request selects short_description, description, and/or resolution_notes, **Then** the fields are returned for the matching tickets within the existing result limits.
2. **Given** the imported database, **When** a governed request filters on resolution_notes being null, **Then** exactly the open tickets (250) match, exercising the existing is-null capability.
3. **Given** the governed query layer, **When** any INSERT, UPDATE, DELETE, TRUNCATE, CREATE, ALTER, or DROP is attempted, **Then** it is rejected with zero database changes, exactly as before this feature.
4. **Given** the new columns, **When** their allowlist configuration is inspected, **Then** the three generated fields are explicitly listed and no other write or arbitrary-SQL path is introduced.

### Edge Cases

- Local endpoint or model mismatch at pre-flight (wrong model ID, endpoint unreachable): the generation step MUST stop and report; no fallback model or provider may be used.
- A model response with invalid JSON or schema-nonconforming entries: bounded retries, then the run MUST fail loudly; it MUST NOT fabricate, patch, or skip the affected tickets.
- Interruption mid-run (process killed, machine restart): the next run MUST resume from the last batch checkpoint and still produce exactly 2057 unique entries — never a restart from scratch, never silently skipped tickets.
- Duplicate or missing ticket IDs in model output: validation MUST fail the entry (every ticket exactly once); duplicates are never silently merged.
- An open ticket (`closed_at` empty): resolution_notes MUST be SQL NULL — never an empty string and never generated placeholder text such as "investigation in progress".
- A closed ticket: resolution_notes MUST be present (1-3 sentences).
- short_description near the length limit: validation MUST fail over-limit entries (about 80 characters) rather than silently truncating them.
- Generated text that contradicts the ticket's structured columns (wrong category/sub_category, wrong priority tone, resolution notes on an open ticket): the deterministic consistency checks MUST fail the artifact.
- Generated text containing credential-like strings, secrets, or personal-data patterns: the automated scan over the artifact MUST find none.
- Prompt or model change after approval: MUST produce a new prompt version and a full regeneration into a new artifact version with new checksums; the previously approved artifact stays intact and pinned.
- Existing database with old schema: the documented clean reset path rebuilds from pinned raw data plus the approved generated artifact; no in-place migration of production data is needed (local demo dataset only).
- Re-import after a completed import: MUST be idempotent and atomic.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The generation step MUST read only the pinned raw ticket records as input; the pinned raw files MUST remain byte-identical (verified by their recorded checksums) after generation.
- **FR-002**: Generation MUST use the project's local llama.cpp endpoint with the exact pinned API model ID, temperature 0, a recorded seed, and response caching disabled; endpoint and model identity MUST be verified before the run (same pre-flight discipline as the rest of the project); no fallback model, hosted provider, or cloud service may be used.
- **FR-003**: Generation MUST use a typed DSPy program (pinned DSPy 3.4.0, lm15 engine) whose output is structured JSON per ticket, validated against a strict JSON schema requiring the ticket ID and exactly the three text fields.
- **FR-004**: Generation MUST process tickets in batches of about 5 per model call, each call returning a JSON array of per-ticket entries; every entry MUST pass zero-tolerance validation before acceptance, with bounded retries per batch and a loud failure (explicit error, non-zero exit) once retries are exhausted — never fabrication, never skipping.
- **FR-005**: The generation run MUST checkpoint after each accepted batch; a restarted run MUST resume from the last checkpoint, MUST NOT restart from scratch, and MUST NOT silently skip tickets; the completed run MUST cover every ticket exactly once.
- **FR-006**: For each ticket the pipeline MUST produce three fields: short_description (one sentence, within a documented limit of about 80 characters, naming the problem and its key detail), description (2-4 sentences with reporter context, scope, trigger, impact, and priority-appropriate wording), and resolution_notes (1-3 sentences with root cause, fix, and verification).
- **FR-007**: resolution_notes MUST be SQL NULL exactly when the ticket is open (no closing timestamp); it MUST be present for every closed ticket.
- **FR-008**: Prompts MUST be built only from the ticket's structured columns (such as category, sub_category, priority, SLA flags, resolution time, reopened) and MUST be versioned, with the prompt version recorded in the provenance manifest.
- **FR-009**: The completed output artifact MUST be pinned, versioned, SHA-256-checksummed, and treated as immutable once human-approved — the same discipline as the project's baseline and optimized-program artifacts.
- **FR-010**: Regeneration MUST be a full run producing a new artifact version with new checksums and an updated manifest; partial or silent regeneration MUST NOT occur, and previously approved artifacts MUST remain intact.
- **FR-011**: A deterministic post-generation validation suite MUST run offline (no model calls) over the completed artifact and MUST verify: JSON schema conformance; 100% ticket coverage (2057 of 2057, every ticket exactly once); zero empty or unresolved fields; the documented length limits; English-only content; absence of credential-like strings, secrets, and personal-data patterns; consistency between each text and its ticket's structured columns (category/sub_category at minimum); and the NULL rule of FR-007. A 100% pass is required before the artifact is a release candidate.
- **FR-012**: A provenance manifest MUST record the exact API model ID, llama.cpp version, temperature 0, seed, prompt version, DSPy version, generator script hash, batch configuration, row count, output SHA-256, and creation timestamp; it MUST be stored with the generated artifact and referenced from the import manifest.
- **FR-013**: The tickets table MUST gain the three generated columns, explicitly marked as generated in schema documentation; all pinned columns MUST keep their pinned values.
- **FR-014**: The database import MUST load the approved pinned generated artifact atomically together with the pinned ticket data (all 2057 rows), MUST be idempotent on re-run, and the clean local reset path MUST remain intact.
- **FR-015**: Import approval MUST require a recorded human data-quality review of generated samples covering every category (the feature's MANUAL GATE); the import MUST NOT be approved on automated checks alone.
- **FR-016**: The three generated columns MUST be exposed read-only through the governed query layer via explicit allowlists; all write operations through the governed layer MUST remain rejected with zero database changes, and no arbitrary-SQL path MUST be introduced.
- **FR-017**: The feature MUST NOT regress existing behavior: the full pre-existing automated test suite (417 tests) MUST pass unchanged, the runtime query path MUST remain free of generation calls, and query behavior over the pre-existing governed columns MUST be unaffected.

### Key Entities *(include if feature involves data)*

- **Generated Ticket Text**: Three synthetic text fields belonging to one ticket (short_description, description, resolution_notes), generated by the pinned local model from the ticket's structured columns. Stored as additive columns on the ticket record; resolution_notes is absent (NULL) for open tickets.
- **Generation Artifact**: The pinned, versioned, SHA-256-checksummed output of one full recorded generation run; immutable once human-approved.
- **Provenance Manifest**: The versioned record of how the artifact was produced (exact model ID, llama.cpp version, temperature, seed, prompt version, DSPy version, generator script hash, batch configuration, row count, output checksum, creation timestamp), enabling audit and full-version regeneration.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Artifact integrity: once human-approved, the generated artifact is pinned and its recorded SHA-256 remains stable; any later change appears only as a new artifact version with new checksums and an updated manifest.
- **SC-002**: Validation gate: the deterministic post-generation validation suite passes 100% of its checks on the generated artifact — schema conformance, coverage of all 2057 tickets exactly once, zero empty fields, length limits, English-only, zero credential-like or personal-data patterns, category/sub_category consistency, and resolution_notes NULL for exactly the 250 open tickets and present for all 1807 closed tickets.
- **SC-003**: Resume reliability: an interrupted generation run resumes from its checkpoint and completes with exactly 2057 unique ticket entries — verified by a test that interrupts and restarts the run — with zero restarts from scratch and zero silently skipped tickets.
- **SC-004**: Provenance completeness: the provenance manifest contains the exact API model ID, llama.cpp version, temperature 0, seed, prompt version, DSPy version, generator script hash, batch configuration, row count, output checksum, and creation timestamp, and the recorded checksums verify against the artifacts on disk.
- **SC-005**: Zero regression: the full pre-existing automated test suite (417 tests) passes with no failures introduced by this feature.
- **SC-006**: Governed exposure: the three generated fields are retrievable through the governed read path (including an is-null filter returning exactly the 250 open tickets), and 100% of attempted write operations through the governed layer are rejected with zero database changes.
- **SC-007**: Human gate: the import is approved only after a documented human data-quality review of generated samples covering all 5 categories; the review record is part of the feature's completion evidence.

## Assumptions

- The human revision decision of 2026-10-12 is binding: generation uses the local pinned Qwen model via a typed DSPy program with strict validation, replacing the earlier hand-authored-template approach.
- Unlike deterministic template filling, model generation is not claimed to be byte-identical across environments; governance is achieved through strict per-entry validation, the deterministic post-generation validation suite, artifact pinning with checksums, and full-version regeneration only.
- The generator is an offline build-time step run by a maintainer against the local endpoint, not part of the runtime query path; it introduces no runtime dependency and no hosted or external provider calls.
- The batch size of about 5 tickets per model call is human-approved; the exact value is recorded in the provenance manifest and may be tuned by the plan within that approval.
- The approved generated artifact follows the same pinning discipline as `artifacts/baseline.json` and `app/ai/optimized_program.json`.
- The dataset is a local demo dataset with a documented clean reset path; no in-place migration of production data is required.
- Field shape targets (sentence counts, about-80-character short-description limit) are enforced by the deterministic validation suite; the plan may tighten them into precise limits.
- Hybrid search (retrieval, ranking, answer integration), any document corpus, and UI changes are explicitly out of scope for this feature.
